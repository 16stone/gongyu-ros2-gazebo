# Physical mission bridge contract

`gongyu.physical_world.PhysicalWorld` reuses World mission, message, booking and controller interfaces. `ros.fleet_episode` drives its four independent Nav2 adapters and two aircraft from actual feedback.

The driver advances the world from the monotone ROS simulation clock, then supplies each actual platform sample via `receive_pose(actor, xyz, speed, wz, sampled_ms, goal_id, navigation_succeeded)`. Position must use the mission map frame and the configured sensor reference height; a ground base pose needs the calibrated sensor offset. Ground arrival additionally needs the final Nav2 result for the matching dispatched goal. Air arrival uses its own position-loop feedback. A sample older than 200 ms or a duplicate/out-of-order sample cannot extend dwell. Missing feedback also removes radio contact.

`submit_move(actor, goal_id, waypoints)` dispatches an actual actuator operation; it must follow intermediate route points and attach this goal ID to subsequent feedback. Dispatch failure retains the unresolved action and occupied resource. It must not fabricate completion or free a channel. Completion requires one second within the calibrated position/speed/angular-speed limits. Task service requires a full service interval of fresh in-region settled feedback; clock-only completion is disabled. Observation quality remains the existing geometry model, not a physical camera measurement.

Readiness is not inferred from the old graph state. Before running policies, the live driver must obtain fresh feedback from every physical entity at its card-defined starting region, after AMCL/TF/navigation and flight startup checks. The current calibration fleet world has different initial coordinates and boundaries from the M1/M2 cards; it cannot be reused as a mission world merely by relabeling positions. The next integration must generate a matching mission scene/map and initial poses, then use the same policy controllers with this backend.

Unit feedback tests are synthetic interface checks. Existing four-car and two-aircraft Gazebo evidence verifies actuator gates separately; none of those runs yet proves a complete PhysicalWorld mission.

`gongyu.timing` is the shared public travel estimate table for bookings, initial/residual forecasts, observation freshness routes, local prepare checks and M2 quotes/provider checks. Directional `travel_time_ms` overrides are explicit positive integer milliseconds on legal edges; absent overrides retain graph distances/speeds. Physical patrol predictions follow the same travel/hold/inspection queue but remain unconfirmed predictions. The physical protocol margin is applied to forecast service receipt and prepare contact horizons, capped at episode end. Actual arrivals/releases still require matching fresh feedback. `freeze_physical.py` freezes a separately named M1 profile with its timing evidence, unmeasured estimates and deadlines before running it; historical cards and failures are unchanged.

The live runner saves local decisions/diagnostics and explicit release-start reasons, and runs to the fixed predeclared horizon so final task-result messages and role releases can complete after payload acceptance. The former all-task early exit is retained only in historical runs and did not verify final coordinator receipt. Its wall-clock guard scales with the predeclared mission horizon. Neither the profile nor a recorded window is a mission-success certificate: independent truth, own deadlines, load/report provenance and actual deliveries must be audited afterward.

SIGINT only sets a stop-request flag; Python checks it at control-loop boundaries and raises KeyboardInterrupt there while ROS context is valid. This avoids injecting asynchronous Python exceptions into native TF calls. Exception traces and the received-signal flag are saved. Each cancel/zero failure is recorded and cannot skip the remaining stop attempts or final evidence writes; unsubscribe failure is also contained. Every ten simulation seconds, new raw/decision/diagnostic records are appended once and an atomic PARTIAL_NOT_FINAL checkpoint is saved. A checkpoint preserves partial evidence after an abrupt process loss, not a final mission result; it does not guarantee recovery from power loss or filesystem failure. Phase18 v1 lost its in-memory event/task buffers during the prior invalid-context cleanup and remains explicitly EVIDENCE_INCOMPLETE. Geometry version2 and recovery verification are separate runs; historical v1 files are unchanged.

The generated physical card now includes `physical_berths` with explicit .8 m parking spacing and .1 m berth acceptance. Use that generated card, not the unchanged graph card, for both scene and backend. A destination claim is allocated before dispatch; source claims remain until matching fresh feedback shows the platform more than .55 m away. Rejected dispatch attempts release only the provisional destination. Actual controller dispatch failure retains unresolved claims. Required intermediate detour corners remain, but nominal endpoint centers are not compulsory waypoints through parked platforms. Nav2 must plan collision avoidance between these goals using actual scans; unit allocation checks do not establish collision-free motion. Changed parking geometry requires a shared physical timing calibration.

The L pair is offset from its nominal node by (.05,0) and (.05,.8), preserving K contact without moving toward the opaque device screen. E departures first align at nominal E x+.25, y=0 before entering the tunnel; arrivals from W still exit at E x+.6 before approaching the allocated E berth. The west centerline route point is(2,0), while W parking x remains1.8 with y+/-.95. The former(1.8,0) alignment caused a real PeerStop beside a vehicle parked at D. The revised centerline clears the configured protection envelope, the recorded D counterexample, W peers and wall corners under the checked position-error assumptions. These checks do not establish full-path dynamic safety.

E berths now use y offsets +/-.95. At the centerline alignment point, even two .1m position errors leave the other E peer beyond the configured PeerStop enclosing radius plus its .22m costmap radius. This is a centerline clearance check, not a full yard-path proof. Physical cards also require six seconds of B3 contact hold measured from actual status execution after arrival, capped at episode end. The same computed deadline is advertised and inserted into the existing command queue for every adaptive policy and resumed patrol. Cards without this physical field retain their graph schedule. Holding can delay the aircraft's own work; old graph forecasts/deadlines still need physical calibration before policy-efficacy claims.

The v3 profile adds a ground same-directed-edge exit guard after a real L departure conflict. A follower waits for fresh predecessor feedback at least3m from its own source berth, or actual completion of that preceding move. A freed parking claim alone(.55m departure) is insufficient: the moving car can still induce an overtaking detour in Nav2's2.5m peer marking/3m clearing range. Different exits and aircraft are not serialized, and the guard does not hold the whole trip. The graph backend and split forecast use the declared12s clearance estimate; the physical backend uses actual clearance rather than a release timer. This is common execution-backend safety scheduling, not new policy access to peer poses; a distributed deployment would need equivalent local sensing or an exit-manager clearance receipt. Deadlines, speed and protection parameters remain unchanged, with a separate v3 scenario and retained v2 failure.


## Local eight-entity runtime profile

The six independent Nav2 stacks need more discovery participant indices than a small default CycloneDDS pool. For the local simulation profile, install `ros-jazzy-rmw-cyclonedds-cpp` and set these in both the launch and episode terminals, from the source root:

```bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
export CYCLONEDDS_URI="$(cat ros/config/cyclonedds_local.xml)"
```

The XML explicitly allows participant indices0..110, keeping the local stacks in a declared bounded pool. It is an execution prerequisite for this profile, not a claim that DDS implementation alone explains all older failures. Keep historical plan environments when auditing older runs. The native collision probe uses separate domain94 and no vehicle connection.
